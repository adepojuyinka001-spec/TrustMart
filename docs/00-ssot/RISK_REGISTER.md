# TrustMart Risk Register

Tracks known security, financial, compliance, and operational risks. Update whenever a new risk is identified (e.g. during an adversarial review pass) or an existing one changes status.

| # | Risk | Category | Severity | Mitigation | Status |
|---|---|---|---|---|---|
| 1 | Live customer-funds flow implemented before a qualified legal/provider structure is approved | Legal / Financial | Critical | Blocked by design — CLAUDE.md §16 requires stop-and-ask; no live provider funding until approved (see Open Decision #1) | Open — mitigated by process gate |
| 2 | Confidential reward/referral rates (0.3% / 0.1% / 0.1%) leaking into customer-facing APIs, frontend bundles, logs, or AI responses | Confidentiality | High | RBAC-gated `RewardPolicyVersion` (not yet built — reward computation is blocked on Open Decision #1); **regression guard now exists regardless**: `apps/api/src/modules/referral/reward-rate-leakage.spec.ts` (static source scan) + a `test/referral.e2e-spec.ts` case (HTTP-boundary check on `GET /referrals/mine`), both passing as of 2026-09-17 — see Decision Log | Open (the underlying reward feature isn't built) — but the leakage regression test itself is closed/passing, ahead of the feature it guards |
| 3 | Buyer contact info exposed via subscription alone, without consent/entitlement check | Privacy | High | Contact access requires subscription + consent + valid interest/lead context + audit (CLAUDE.md §5) — `ContactAccessService`/`ContactAccessController` built and covered by `test/engagement.e2e-spec.ts` | Mitigated — built and tested. `ContactAccessService.hasActiveEntitlement()`'s real subscription check still stubbed pending Open Decision #1 (Subscription/SubscriptionPayment activation) — re-verify this row once that's wired |
| 4 | n8n or AI granted ability to write financial tables, set Escrow/payment status, or move funds | Financial integrity | Critical | Backend-only financial writes; n8n/AI call authenticated APIs only, never direct DB access (CLAUDE.md §11–12). The Financial Ledger engine (`LedgerService`, 2026-09-15) enforces this by construction — it exposes no endpoint that lets any caller, including n8n/AI, post an unbalanced or unverified entry; only read endpoints are exposed at all today. TrustGuard risk detection (`RiskCaseService`, 2026-09-17) is the same pattern — detection-only, no endpoint that suspends an account or removes a listing | Open — no financial-writing endpoint exists yet at all (mitigated by absence); re-verify when Phase 6 payment integration adds one |
| 5 | Matching threshold/weights or listing lifecycle/pricing hard-coded instead of configurable | Business flexibility | Medium | PlatformConfiguration-driven values, no hard-coded constants (CLAUDE.md §4) — built, with an admin UI (`/admin/config`) and regression test coverage | Mitigated — built and tested |
| 6 | Payment marked successful from unverified signal (screenshot, claim, unverified webhook) | Financial integrity | Critical | Mandatory provider verification pipeline before ledger posting (CLAUDE.md §9) — the ledger-posting *half* of this (`LedgerService.postJournal()`: balanced, idempotent via `(source, reference)` external reference, immutable) is built and tested (2026-09-15); the provider-verification half (actually confirming a webhook/signal is real before ever calling `postJournal()`) does not exist and can't until a payment provider is chosen | Open — enforce when Finance/Payments provider integration is built (Open Decision #1) |
| 7 | `trustmart_dev` has accumulated a large volume of test/e2e-fixture data over the session (e.g. 650+ throwaway accounts sharing this dev machine's `localhost` registration IP, dozens of duplicate test categories/listings from before test-DB isolation was fixed on 2026-09-08) | Operational / data hygiene | Low | None systematic yet — cleaned up ad hoc, case by case, whenever a specific issue surfaced (documented individually across several Decision Log entries as "dev-data hygiene, round N") | Open — not a security/financial risk, but real enough that it already produced one live TrustGuard false-positive (655-account "duplicate accounts" case, dismissed 2026-09-17) and inflates `/admin/analytics` figures (e.g. "660 registered users" is almost entirely test data). Consider a one-time cleanup script, or resetting `trustmart_dev` from a fresh migrate+seed, before this is ever used for a real demo |

## How to use this file
- Add rows as risks are identified, especially during the "Adversarial Review" prompt pass.
- Never close a Critical/High risk without a corresponding regression test.
