## 2026-09-07 — Wired Marketplace Core (Category/Listing/BuyerRequest/Matching) into AppModule; built the Matching orchestration layer
- **Context:** Founder asked to continue autonomously through the implementation phases without waiting for per-step approval, while still stopping for anything on CLAUDE.md's own Stop Conditions list (legal/funds structure, provider selection, security weakening, confidential-rate exposure, destructive migrations, etc.). This entry and the next few implementation steps proceed under that standing instruction.
- **Finding:** `CategoryModule`, `ListingModule`, `BuyerRequestModule` had services/controllers/DTOs written (Phase 2) but were never imported into `AppModule` — none of their endpoints were actually reachable. Additionally, both `ListingService` and `BuyerRequestService` already imported and called `MatchingEngineService` from `../matching/matching-engine.service`, but that file did not exist — only the pure `matching-engine.util.ts` scorer (Phase 3 groundwork) was present. The app would not have compiled if these modules had been wired in as-is.
- **Built:** `MatchingEngineService` (orchestration: loads active listings/buyer-requests for a subcategory, builds `evaluateMatch()` input from stored `MatchingProfile`/`MatchingCriterion` weights and buyer requirement overrides, upserts `Match`/`MatchCriterionResult`, applies the configurable threshold, classifies score bands, emits `marketplace.match.created` via `@nestjs/event-emitter` only on newly-qualifying pairs), `MatchingProfileService` (versioned admin-managed weight sets — creating a new version deactivates the previous one), `MatchingController` (admin profile management gated on `matching:manage`; buyer/seller match views, ownership-scoped, seller view excludes buyer budget/requirement data per CLAUDE.md SS13).
- **Registered** `CategoryModule`, `ListingModule`, `BuyerRequestModule`, `MatchingModule`, and `EventEmitterModule.forRoot()` in `AppModule` (the `@nestjs/event-emitter` package was a declared dependency but not actually installed — `pnpm install` via `npx pnpm@9` fixed this; `npx pnpm@latest` resolved to an unstable 12.3.4 that failed with an internal path error, so pinning to `@9` — matching the lockfile's `lockfileVersion: '9.0'` — is now the working invocation on this machine).
- **Bug found and fixed:** Prisma `BigInt` fields (money/budget) can't be JSON-serialized by Express. A `toJSON` polyfill existed in `main.ts`'s `bootstrap()` but never ran for e2e tests (which construct `AppModule` directly, bypassing `main.ts`) or any other non-`main.ts` entry point. Moved it to `src/bigint-json.polyfill.ts`, imported for its side effect at the top of `app.module.ts`. This was a real, previously-undiscovered defect — it just never surfaced because the affected modules were never reachable before this pass.
- **Seed data extended:** `category:manage`, `listing:moderate`, `matching:manage` permissions were referenced by existing `@RequirePermission(...)` guards but never seeded — meaning ADMIN would have silently failed every one of those checks. Added them, plus `marketplace.match_budget_weight_percent` / `marketplace.match_location_weight_percent` (25% each, matching the SSOT's illustrative Real Estate weight example — an initial default, not a fixed rule).
- **Verified:** `nest build` clean; 24/24 unit tests pass; 7/7 e2e tests pass (4 pre-existing Shared Core + 3 new `test/matching.e2e-spec.ts` covering the full category→subcategory→attribute→listing→buyer-request→match flow, hard-requirement disqualification, threshold qualification, seller-facing privacy, and RBAC on category/matching-profile management).
- **Reasoning:** Completes the wiring gap left from Phase 2 and delivers Phase 3's core (deterministic Matching). No business rule, fee, financial, or security-authorization behavior was invented — thresholds/weights remain `PlatformConfiguration`-driven per CLAUDE.md SS4/SS9, and the bug fixes restore documented intent (BigInt-safe money, RBAC permissions that were already assumed to exist) rather than introducing new behavior.

## 2026-09-07 — Built Interest / Lead / Contact Access (rest of Phase 3)
- **Context:** Continuation of the same standing "proceed autonomously, stop only on CLAUDE.md's own Stop Conditions" instruction as the previous entry.
- **Built:** New `EngagementModule` (`apps/api/src/modules/engagement/`) covering:
  - `InterestService` — "I'm Interested" (CLAUDE.md SS11) creates an `Interest` and its `Lead` atomically in one transaction; rejects self-interest and duplicate interest on the same listing; optional `matchId` is verified to actually belong to the requesting buyer and listing.
  - `LeadService` — seller-driven status transitions through the full flow (NEW→VIEWED→CONTACTED→INSPECTION_SCHEDULED→NEGOTIATING→TRANSACTION_STARTED→WON/LOST); every transition is recorded as a `LeadActivity`; WON/LOST/SPAM_FRAUD are terminal (no further transition accepted).
  - `ContactAccessService` — enforces the buyer-contact-privacy rule (CLAUDE.md SS5/SS13). **This is the most important decision in this entry**: the subscription/entitlement check (`hasActiveEntitlement()`) is hard-coded to always return `false`, because Subscription/Entitlement (Phase 4) does not exist in this codebase yet. This means contact access **cannot currently be granted to any seller, under any circumstances** — a deliberate fail-closed default, not a placeholder bug. The method and its comment explicitly say not to "temporarily" flip it to unblock testing; the e2e test in this pass asserts the denial, not a workaround. Every access attempt (granted or denied) is recorded in a new `ContactAccessGrant` table and the generic `AuditEvent` log.
- **Schema additions** (additive-only migration, `20260907012744_interests_contact_leads`, no drops/truncates): `SavedListing`, `Interest`, `Lead`, `LeadActivity`, `ContactAccessGrant`, `LeadStatus` enum. Reused the existing `Consent` model (`ConsentType.BUYER_CONTACT_SHARE`) for buyer consent rather than adding a new consent table.
- **Seed data extended:** `lead:moderate` permission (RISK_ANALYST + ADMIN) for the SPAM_FRAUD moderation action.
- **Verified:** `nest build` clean; 24/24 unit tests pass; 10/10 e2e tests pass (7 pre-existing + 3 new in `test/engagement.e2e-spec.ts`), including: interest/lead creation with self-interest and duplicate-interest rejection, lead status progression and terminal-state enforcement, RBAC positive/negative on SPAM_FRAUD moderation, and — the safety-critical case — contact access denied even when the buyer has explicitly granted `BUYER_CONTACT_SHARE` consent, with the denial reason and an audit row both asserted.
- **Reasoning:** Completes Phase 3 (Matching & Opportunity) per the implementation order. No financial, fee, or security-authorization behavior was invented; the contact-access gate is intentionally more restrictive than the future end state (fails closed instead of guessing at an entitlement check), consistent with CLAUDE.md SS16 ("stop if... confidential/authorization would be weakened") — the safe direction to err in is denial, not invented permissiveness.

## 2026-09-07 — Subscription Plan/Entitlement catalog, deliberately without activation
- **Decision point:** Before building Phase 4 (Subscription), asked the founder how to handle activation given no payment provider is chosen yet (Open Decision #1). Options were: (a) catalog only, no activation; (b) also add a manual admin-attested activation stand-in; (c) skip Subscription entirely for now. **Founder chose (a).**
- **Built:** `SubscriptionPlanService`/`SubscriptionPlanController` (`apps/api/src/modules/subscription/`) — admin-managed (`subscription:manage`) `SubscriptionPlan` + generic key/value `SubscriptionEntitlement`. Public read of active plans (buyers/sellers need to see pricing before subscribing); admin-only create/update/entitlement-upsert. Plan core terms (key, price, currency, billing period) are immutable after creation by design — changing them would retroactively affect anyone already on the plan; the pattern is to create a new plan and deactivate the old one, same as `MatchingProfile` versioning.
- **Explicitly not built:** `Subscription` (a seller's actual paid instance), `SubscriptionPayment`, and any activation flow. Building any of these — even a "manual admin marks it paid" stand-in — would mean establishing a real money-collection path before the payment-provider and legal/funds-structure decisions (Open Decision #1) are made, which CLAUDE.md's Stop Conditions (SS16) flag as founder-only territory. `ContactAccessService.hasActiveEntitlement()` therefore continues to always return `false`, unchanged from the previous entry.
- **Seed data:** `subscription:manage` permission (ADMIN only); illustrative starter catalog (FREE, WEEKLY_SELLER at ₦5,000/week, MONTHLY_SELLER at ₦15,000/month, matching the SSOT's introductory pricing) with example entitlement rows (`listing_limit`, `lead_contact_access`) — entitlement *meaning* is not enforced by any code yet, this is catalog data only.
- **Verified:** `nest build` clean; 24/24 unit tests pass; 12/12 e2e tests pass (10 pre-existing + 2 new in `test/subscription.e2e-spec.ts`), including RBAC positive/negative on plan/entitlement management, duplicate-key rejection, and active-vs-all listing visibility.
- **Reasoning:** Delivers the non-financial half of Phase 4 without pre-empting a decision that is explicitly reserved for the founder/legal per CLAUDE.md SS16 and SS39 ("do not invent... production payment/banking provider... final production fee collection mechanics").
